# 寫作：S5–S7

> 站專屬的部分（要稽核哪些段落、站的寫作規範）放在站設定，這裡只留通用規則與例子。

---

## S5　大綱

根據 S1–S4 的研究，產出文章大綱，包含：

- H1 標題（含主關鍵字，自然放在前半段）
- 所有 H2/H3 標題（每個次要關鍵字至少對應一個 H2 或 H3）
- 每個段落的核心內容摘要（3-4 句）
- FAQ 預計問題（至少 3-5 題）
- 預計的內部連結目標（Pillar Page + 相關 Cluster：用 S4 記在 state.json 的 `keyword_plan.pillar_url`、`sibling_urls`，只連「已上線」的頁；沒有 keyword plan 時從 content-inventory 挑主題相關的頁）。一個有網址的目標都沒有 → 大綱寫「本篇沒有內部連結目標」，照常往下，不要為了湊連結去找清單以外的頁

大綱順序照 core-principles「H2／H3 先滿足關鍵字，再放差異化內容」。

- **互動模式**：停下來讓使用者確認大綱，確認後再開始撰寫全文（gate `outline`）。
- **auto 模式**：**不等確認**，但必須把大綱**與切角理由**寫進 `runs/{slug}/intent-report.md`，最終報告要呈現。

## S6　撰稿

### 寫作風格（唯一權威）

撰寫前，**必須先讀取站的寫作規範**，並嚴格遵循其中所有規則：

| 讀什麼 | 有就讀 | 沒有時 |
|---|---|---|
| 怎麼說（語氣、人稱、用詞） | `{站}/brand-voice.md` | `~/article-engine/language/{language}.md` 的預設語氣 |
| 要守什麼（結構、取捨、模板、禁止事項） | `{站}/writing-guide.md` | — |
| 跟主題無關的寫作原則 | [../writing/core-principles.md](../writing/core-principles.md)（一律讀） | — |

站的 writing-guide 跟 core-principles 有衝突時，以站的為準。

（例：拜拜日曆的 writing-guide 由 `/learn-writing` 持續維護演化，記錄了語氣用詞、文章結構、內容取捨等所有寫作風格規範。）

### 參考既有文章的內容取捨

撰寫前，讀取站上最近發布的 `profile.writing.reference_recent_articles` 篇文章（預設 2 篇）：從 `{站}/content-inventory.csv` 挑發布日最近、內容型態是文章、而且有網址的列，照網址用讀取來源轉接器的「抓回」動作抓現行版本。

**清單裡沒有可參考的文章**（清單是空的、或只有還沒網址的稿）→ 跳過這一段，只照 brand voice 與寫作規則寫，state.json 的 `defaults_used` 記「沒有可參考的既有文章」。不要改去讀清單以外的頁。

有文章時萃取以下三點：

1. **內容取捨**：這篇文章選擇放了什麼、沒放什麼？哪些段落著墨較多、哪些一筆帶過或直接省略？
2. **寫作態度**：面對這個主題時，作者用什麼立場和態度在寫？是解釋型、鼓勵型、還是中性陳述型？
3. **格式慣例**：frontmatter 欄位怎麼填（`profile.frontmatter.fields` 每個欄位的寫法）；開頭內部連結段落放在哪個位置、句型長什麼樣、連到哪些目標（例：拜拜日曆連同月 sibling 神明 + Pillar）。

將觀察結果作為本次撰寫的參考依據，與站的寫作規範互補使用。
如果寫作規範有明確規則的地方，以寫作規範為準；
寫作規範還沒覆蓋到的地方，則以既有文章的做法為參考。

站上還沒有文章（零篇）時跳過這一段，報告註明。

### SEO 核心規則

**關鍵字佈局**（詳細策略見 [../writing/keyword-layout.md](../writing/keyword-layout.md)）：

- 主關鍵字出現在：Title、H1、URL、Meta Description、首段前 100 字、結論
- 主關鍵字全文出現 3-6 次，自然融入
- 每個次要關鍵字在其對應的 H2/H3 段落出現 1-2 次
- 禁止：同一個詞連續出現、每段都塞主關鍵字、同義詞不自然堆疊

**文章結構**：

- H2/H3 標題盡量寫成完整問句（AI 搜尋友善）
- 開頭 2-3 句直接回答文章核心問題（AI Overview 優化）
- 提供具體數字和清單，避免模糊描述
- FAQ 段落使用 `### Q：` 格式，每個 QA 獨立成段
- 流程類內容使用編號步驟格式

**內部連結**（詳細規則見 [../writing/seo-rules.md](../writing/seo-rules.md)）：

- Cluster → Pillar：1-2 個連結，使用包含 Pillar 主關鍵字的錨點文字
- Cluster ↔ Cluster：同 Pillar 下互連 1-3 個
- 整體密度：每 1,000 字 3-5 個內部連結
- 外部連結：2-3 個權威來源
- 禁止使用「點這裡」「看更多」等無描述性錨點文字

內部連結只能用 `{站}/content-inventory.csv` 網址欄裡有的頁，格式照 `profile.writing.internal_link_format` 與 `profile.site.article_url_pattern`。清單涵蓋狀態是「未確認」或「失敗」時照用，報告註明可連的頁可能更多。沒有 keyword plan 時 pillar 相關的條文不適用，報告標 ⚠️

Pillar Page 或同主題的 Cluster **還沒有網址**（未上線、未確認、只有草稿）→ 不放連結、不放佔位連結，報告的提醒列出「{頁名} 上線後回來補連結」。清單完全沒有可連的頁 → 這篇沒有內部連結，照常產出。

**導流**（`profile.site.cta` 有填時）：文末行動呼籲照 `cta.text`＋`cta.url`；內文最多 `cta.max_inline_mentions` 處自然提到產品。

### S6b　潤飾與補充

1. **外部連結規劃**：找出應連結到外部資源的詞彙或概念，在文中標註（不要只列在文末）。
2. **圖片規劃**：為關鍵段落建議圖片，包含描述（圖片應呈現什麼）和 alt text 建議。
3. **自我檢查**：對照 [../writing/seo-rules.md](../writing/seo-rules.md) 中的自檢表，快速掃一遍確認沒有遺漏。

### S6c　輸出

- 文章草稿存放於 `{站}/runs/{slug}/draft.md`
- 意圖研究報告存放於 `{站}/runs/{slug}/intent-report.md`
- **永遠建立新檔案，不覆蓋既有檔案**（`強制重寫` 時 slug 加 `-v2`、`-v3`）

#### 文章檔案必含 YAML frontmatter

每篇草稿的**最開頭**必須是 frontmatter block，欄位照 `profile.frontmatter.fields`，不可缺。預設欄位：

```markdown
---
title: "{文章 H1 標題，含主關鍵字}"
slug: {URL slug，連字號分隔，含主關鍵字}
date: {YYYY-MM-DD HH:MM:SS，撰寫當下時間}
modified: {YYYY-MM-DD HH:MM:SS，最後修改時間}
status: draft
excerpt: "{60-80 中文字的 meta description，含主關鍵字，當廣告文案寫}"
---
```

欄位對應關係：

- `title` ↔ S6 SEO 規則的 Title
- `slug` ↔ URL 結構（與 runs/ 資料夾名一致；樣式照 `profile.frontmatter.slug_style`）
- `excerpt` ↔ Meta Description（seo-rules.md 60-80 字規則套用於此欄位；字數照 `profile.frontmatter.excerpt_length`）
- `status` 新草稿一律填 `profile.frontmatter.draft_status_value`（預設 `draft`）

範例可參考站上任一已發布文章的開頭（S6「參考既有文章」抓回的那幾篇）。

## S7　出處稽核（hard gate，只稽核高風險段落）

初稿寫完後**單獨做這一件事**，不要和潤飾混在一起。對著寫好的全文跑，這是過不了就不能進下一步的硬閘門。

> 為什麼要獨立成一步：「每個論斷都要有出處」寫在指南裡、靠生成當下自律執行會在長文後段衰減失效（農場文就是這樣漏出去的）。把它搬成流程固定節點、對成品文字稽核，才會真的被執行。

### S7.1　圈出要稽核的段落

只稽核 H2/H3 標題命中**站的 audit rule 列的高風險段落清單**的段落，其他段落這步一律跳過。

- 有 `{站}/audit-rule.md` → 用它的「要稽核的段落」清單。
- 沒有 → 用 `~/article-engine/audit-presets/{audit.preset}.md` 的清單。

> 例：拜拜日曆的清單（「職司／能求什麼」主題段）：
> - 「X 管什麼」「X 掌管什麼」
> - 「X 可以求什麼」「求什麼」
> - 「X 保佑什麼」
>
> （清單之後會擴充。）

### S7.2　逐句分型，並分**來源層級**

對命中段落裡**每一個具體的肯定論斷**（含每一個 bullet）做兩件事：

**(1) 分型**，寫進 state.json 的 `claims`：

| 論斷類型 | 例子 | 通用預設處置 |
|---|---|---|
| 事實型 | 農曆日期、法規條文、水星逆行起訖 | 查到可靠來源才保留；查不到就刪 |
| 推算型 | 牌型機率、「水逆在牡羊座影響第一宮」 | 有擴充檢查時交給 S9；沒有時轉人工檢查清單 |
| 傳統說法型 | 神明職司、星座個性、吉凶宜忌 | 不裁定真假；段落層級交代出自哪個傳統，多說並列 |
| 建議型 | 供品怎麼準備、新手先打哪種賽 | 檢查是否符合 writing guide 的立場；沒有就只檢查有沒有自相矛盾 |
| 合規 | 醫療、投資、法律、賭博、保證效果 | 不給醫療與投資建議、不保證效果，必要時加免責區塊 |

站的 audit rule 對某一型有自己的處置時，以站的為準。

**(2) 套用來源分級**（站的 writing guide 或 core-principles 的「每個具體論斷，生成當下就要二選一」）。重點不是「有沒有出處」，是「出處夠不夠力」（強＝一級古籍篇名＋引文／官方規範／具名專書＋引文／官方沿革或官方文件；弱＝維基／百科／部落格／二手彙整）：

| 此刻句中最強的出處 | 動作 |
|---|---|
| 強來源（且寫進句子） | 保留 |
| 只有弱來源，或無出處、但查得到一級來源 | 用 WebSearch / WebFetch **往一級來源挖**（例：拜拜日曆挖《明史·禮志》、地方志、具名專書等），把**真實一級**出處＋（可的話）原文寫進句子 |
| 查不到一級來源 | 降成「相傳／民間說法」這類語氣（依論斷類型與語言包的說法）且不展開細節，或刪 |

**維基當跳板、不要停在維基**：維基只是找一級來源的入口，順它的引註爬到背後的一級來源；禁止用「根據維基百科的整理…」當權威背書（這仍是弱來源）。

**NEVER 為了過關捏造出處**：不准生一個看起來像出處的字串（假《經名》、空泛的「據古籍記載」、沒書名的「某人記載過」）來騙過稽核。出處要嘛是查得到的真實一級來源、要嘛就降語氣。捏假出處比缺出處更糟。

### S7.3　閘門

命中段落裡只要還有「肯定語氣但出處不夠力（無出處、或只停在維基／部落格）」的論斷，就**不准進 S8**。每條都掛到一級來源、或降成較弱的語氣才放行。

推算型論斷沒有對應的擴充檢查時，不在這裡擋，記進 state.json 的 `manual_checks`，S9 轉成人工檢查清單。

**維基的例外**依站的 writing guide（例：拜拜日曆允許「爬到底發現維基已經是最完整、最真實的來源」時直接寫「根據維基百科的記載…」）。
