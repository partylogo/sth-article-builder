# 第 2 段：站點資料（三個部分）

給使用者看的開場一句：「這段分三個部分：2-1 網站基本資料、2-2 讀者與導流、2-3 既有文章要不要收。」照順序做，每個部分寫完檔才給下一張卡：

| 部分 | 設定什麼 | 寫進 |
|---|---|---|
| 2-1 | 網站基本資料：網址、語言地區、品牌名、新文章的網址樣式 | `site.domain`、`canonical_base`、`article_url_pattern`、`language`、`region`、`brand` |
| 2-2 | 讀者與導流：讀者是誰、讀完要去哪 | `site.audience`、`site.cta` |
| 2-3 | 既有文章要不要收進清單 | `content_inventory`、`cannibalization`、`adapters.read_source`；content-inventory.csv |

三個部分都寫完，`setup.parts.site_data` 設 done。單獨補某一部分：`/sth-article-builder setup 網站資料`／`讀者`／`既有文章`。

## 2-1：網站基本資料

### 說明卡

**這段設定什麼**：網站的網址、語言地區、品牌名怎麼寫、新文章的網址長什麼樣。

**為什麼需要**：
- 重複內容檢查：寫新文章前，搜你的網站有沒有寫過同一個題目
- 查搜尋量、看搜尋結果用的國家和語言
- 文章裡的品牌名、內部連結的網址格式、發布後去哪裡確認文章上線

**要決定什麼**：
- 網址（還沒上線就說還沒上線）
- 語言與地區（例：繁體中文、台灣）
- 品牌名的正確寫法；網站上有好幾種寫法並存時，哪個對
- 新文章的網址樣式（例：`/blog/{代稱}/`）

**方法**

| 方法 | 做什麼 | 你要準備 | 時間 | 會動到外部嗎 |
|---|---|---|---|---|
| A. 手動輸入 | 你直接輸入四個值 | 四個值 | 1 分鐘 | 不會 |
| B. 輸入網址 | 你輸入網址，我讀首頁和網站地圖，推測四個值附依據給你確認 | 網址 | 1–2 分鐘 | 只讀 |
| C. 讀程式碼 | 我讀網站程式碼裡的設定檔與路由，推測四個值附依據給你確認 | 網站程式碼資料夾 | 2–3 分鐘 | 只讀 |

不能跳過。B、C 可以一起選，兩邊結果對照。

### 方法 A 的做法（手動輸入）

依序問網址、語言地區、品牌名、新文章網址樣式。網址要確認正式版本：打開一次，看有沒有轉到 www 或 https，結果寫進 `canonical_base`。網址樣式不確定時說「不確定」，`article_url_pattern` 先留空，狀態畫面標 ⚠️。

### 方法 B 的做法（輸入網址）

照 `~/article-engine/adapters/read-source/website.md`：

1. 抓首頁 HTML。被擋就照轉接器的退路（帶 UA → 瀏覽器）。哪一種方法成功就記進 `adapters.read_source.website`（例：需要 UA 就填 `user_agent`）。
2. 偵測，每一項記依據：

   | 項目 | 從哪裡看 |
   |---|---|
   | 網址正式版本 | 有沒有 www、http 轉 https、redirect 到哪 |
   | 語言 | `<html lang>`、內文字元 |
   | 品牌名 | `og:site_name`、`<title>` 的固定後綴、logo 的 alt |
   | 網址樣式 | 網站地圖裡各網址前綴的頁數（只讀網址清單，不逐頁抓）；子網站地圖網址裡的 `&amp;` 要還原成 `&` |
   | 平台（附帶，給第 6 段用） | `<meta name="generator">`、`/wp-json/` 有沒有回應、`/ghost/api/`、`__NEXT_DATA__`、`/_astro/` 路徑、HTTP 標頭 |

3. 結果整理成一張表（項目、推測、依據）給使用者確認。網址樣式有好幾種（例：`/blog/` 和 `/news/`）時，列出各前綴的頁數與一兩個網址，問「新文章要放哪一種？」

### 方法 C 的做法（讀程式碼）

1. profile 還沒有 `site.repo_path` → 問「網站程式碼在哪？」，讓使用者直接輸入路徑，不給選項。確認資料夾存在，寫進 `site.repo_path`。
2. 資料夾裡有好幾個 app（monorepo）時，列出來問哪一個是網站。
3. 只讀，找：
   - 正式網址：`astro.config.*` 的 `site`、`next.config.*`、`package.json` 的 `homepage`、`CNAME`、`.env*` 裡名字含 `SITE_URL`／`BASE_URL` 的變數（只讀變數名稱與這一個值）、`sitemap.*`、`robots.*`
   - 語言：框架的 i18n 設定、根 layout 的 `lang`
   - 品牌名：layout 的 `<title>` 樣板、manifest 的 `name`
   - 網址樣式：路由資料夾（例：`src/pages/blog/[slug].astro`）；內容不在 repo、從 API 讀時（路由檔裡有 fetch），記下來並在結果裡說「這個前綴的文章不在程式碼裡，第 6 段上稿要透過後台」
4. 結果表格給使用者確認，同 B。

### 寫檔

profile 的 `site.domain`、`canonical_base`、`article_url_pattern`、`language`、`region`、`brand.name`、`brand.variants_to_fix`。還沒上線：`site.domain` 留空，2-3 只剩 B（不放既有文章）。

`site.language` 對應不到 `~/article-engine/language/` 底下的語言包時，照實說「目前只有 zh-TW 語言包」，寫進 skill-issues.md。

`research.community_sources` 依語言填預設，不問，在完成訊息裡列出：

| 語言 | 預設社群來源 |
|---|---|
| zh-TW | threads.net、ptt.cc、dcard.tw |
| 其他 | reddit.com、quora.com |

## 2-2：讀者與導流

### 說明卡

**這段設定什麼**：文章寫給誰看，讀者看完你希望他去哪裡。

**為什麼需要**：
- 讀者決定研究搜尋意圖時看哪些問題、大綱寫多深、哪些術語要白話解釋
- 導流決定文末的行動呼籲寫什麼、連去哪；內文最多自然提到產品 1 次

**要決定什麼**：
- 讀者是誰（一句話）
- 讀完要去哪：按鈕文字、網址

**方法**

| 方法 | 做什麼 | 你要準備 | 時間 | 會動到外部嗎 |
|---|---|---|---|---|
| A. 手動輸入 | 你直接輸入讀者描述、按鈕文字與網址 | 兩個答案 | 2 分鐘 | 不會 |
| B. 輸入產品網址 | 你輸入網址，我讀那一頁和關於頁，提讀者與導流按鈕的候選，附出處給你挑或改 | 網址（2-1 已經有就不用） | 1–2 分鐘 | 只讀 |

**推薦**：2-1 選了 B（已經讀過首頁）時推薦 B，因為只要多讀關於頁。其他情況不標。

不能跳過。

### 方法 A 的做法（手動輸入）

依序問兩題。導流沒有就說沒有，`site.cta` 留空（文末不放行動呼籲）。

### 方法 B 的做法（輸入產品網址）

1. 讀使用者給的網址（2-1 已讀過首頁就沿用）、`/about` 或關於頁、導覽列與頁面上最醒目的按鈕（下載、註冊、產品頁）。
2. 讀者給 1–2 個候選，每個附出處原文；導流列出找到的按鈕文字與網址。
3. 問：
   ```
   讀者是誰？我從 {出處} 看到「{原文}」，候選：
   1. {候選 1}
   2. {候選 2}
   3. 自己寫一句
   ```
   導流同樣列候選＋「自己寫」。候選加「自己寫」超過 4 個時拆成兩題。

### 寫檔

`site.audience`、`site.cta.text`、`site.cta.url`、`site.cta.max_inline_mentions`（預設 1）。`site.cta.angle_bias` 不問，留空（選題照搜尋成效最大的角度寫）。

## 2-3：既有文章要不要收進清單

### 說明卡

**這段設定什麼**：網站上已經有的文章，要不要列進「現有文章清單」（`content-inventory.csv`）。

**為什麼需要**：清單有三個用途：
- 重複內容檢查：寫新文章前，比對清單裡有沒有寫過同一個題目
- 內部連結只連清單裡的文章
- 寫稿時參考清單裡最近的文章怎麼寫

**要決定什麼**：
- 收不收既有文章
- 收的話，哪些網址算文章

**方法**

| 方法 | 會怎樣 | 你要準備 | 時間 | 會動到外部嗎 |
|---|---|---|---|---|
| A. 全部收 | 我讀網站列出文章。舊文章會參與重複內容檢查、可以被連結、會被當寫作參考 | 不用 | 看文章數，幾分鐘到十幾分鐘 | 只讀 |
| B. 不放既有文章，只收後面新寫的文章 | 清單從空的開始。舊文章不會被連結、不會被當參考；重複內容檢查仍會搜你的網站，搜到舊文章照樣提醒。之後想收舊文章，打 `/sth-article-builder setup 既有文章` 選 A | 不用 | 0 | 不會 |

**推薦**：使用者說過「舊文章不要當參考」之類的話時推薦 B。其他情況不標。

### 方法 A 的做法（全部收）

1. **先讀網站地圖的網址清單**（2-1 選 B 讀過就沿用），照前綴數頁數，不逐頁抓。
2. **問哪些前綴算文章**：列出各前綴的頁數與一兩個網址，多選。答案寫進 `cannibalization.include_url_patterns`。
3. **只抓選中的前綴**：照 `website.md` 的「列出」逐頁抽標題、H1、發布日，寫進 `{站}/content-inventory.csv`，`written_by_engine` 填「基準」。沒選中的網址也寫進清單（`content_type` 填 other），但不逐頁抓。逾時的頁重試一次。
4. **讀不到時才問別的讀法**：網站地圖讀不到，或讀到的文章數明顯不完整（例：列表頁看得到、網站地圖沒有），照實說哪裡讀不到，問「可以從哪裡讀？」：
   - 讀 WordPress API（`wp-rest.md`；2-1 已經偵測到不是 WordPress 就不列這項）
   - 讀網站程式碼（`repo.md`；profile 還沒有 `site.repo_path` 時這時才問路徑。找內容資料夾時排除每一層的 `docs/`，候選要有 title 欄位、而且對得到網站網址）
   - 先這樣就好
   多個來源以網址為鍵合併；兩邊數量對不上 → 寫出差幾篇、各舉一個例子，不自己判斷誰對。
5. 結果給使用者確認：「收了 N 篇文章，涵蓋狀態：{已確認完整／未確認}」。涵蓋狀態看「新文章放的那個前綴」有沒有被完整讀到，不是看用了哪種讀法。

### 方法 B 的做法（不放既有文章）

不讀網站。建一個只有表頭的 `content-inventory.csv`（格式見 `website.md`），開頭註解寫 `# coverage: 只收本系統`（`site.domain` 空的時候寫 `網站未上線`）。

### 寫檔

```yaml
content_inventory:
  include_existing: true    # A＝true；B＝false
adapters:
  read_source:
    primary: website
    extra: []               # A 讀不到時加讀的來源，例：[wp-rest]、[repo]
```

`cannibalization.include_url_patterns` 只有 A 會填。
